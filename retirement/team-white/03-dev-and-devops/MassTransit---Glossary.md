# MassTransit - Glossary

> Source: [Team White SharePoint](https://ascensus0.sharepoint.com/sites/TeamWhiteCF/SitePages/MTP-MassTransit---Glossary-299369852.aspx) | Created: 2025-01-02 | Last modified: 2025-01-02 | Author: Diego Emanuel Travieso | Last editor: Diego Emanuel Travieso

---

In order to have a common understanding of the terms used in MassTransit here are a few keywords with their meaning.

| **Keyword** | **Definition** |
| --- | --- |
| **Saga** | Is a list of tasks that have to be executed in a particular order to accomplish a particular goal. The implementation of a Saga is done in a Saga State Machine. The way in that a Saga State Machine handles the conditions, states, etc. (Behaviors) is called Orchestration. |
| **Saga State Machine** | <br>Is the technical implementation of a Saga. It has Initial and Final state as a start, and then it will have as many different states and behaviors as the Saga requires. It is the Orchestrator that is able to fire and consume events related to the Saga, executing the behaviors programmed to transition between its states and changing its own values.<br>A Saga State Machine is a Consumer, that will be listening to all the events relevant to its behavior. And also as a result of a behavior it can publish events to be consumed by other components.<br> |
| **Orchestrator** | It is the name that is usually given to the**Saga State Machine** , which is the component responsible for processing the **Orchestration** of a Saga. |
| **State** | The **Saga State Machine**  defines in its **Orchestration** all the different States that it can be in. Each State should have a meaning and a purpose that represent the stages of the **Saga** . |
| **Behavior** | It is the way a **Saga State Machine**  reacts to specific combinations of its own **State** and specific events being consumed. |
| **Consumer** | Is a component that is able to "listen" to a certain type of event and process it. Usually publishing events with the results of that processing so the **Saga State Machine**  can consume. |
| **Saga Activity** | <br>Although there is more than one way to actually implement this concept in code, we can define the **Saga Activity**  as the task or tasks executed in the **Behavior** of the **Saga State Machine** .<br>It will be what is executed is between a combination of **State-EventType**  condition and a transition to another **State** in the **State Machine.**<br>It can be implemented simply by a code block in the State Machine Behavior definition, by an extension method of the behavior or by using another class that implements the Activity<TInstance, TData> interface.<br> |
| **Distributed Transaction** | It is a group of tasks that have to be executed in a particular order and should be processed as a whole. Meaning that if at any point in the execution one of the steps fail, the whole transaction has to be rolled back, leaving everything as it was before it started executing. |
| **Routing Slip** | A Routing Slip is a list of dynamic tasks that have to be executed in order creating a **Distributed Transaction** . It will be defined and executed within a **Consumer** of a **Saga** . |
| **Routing Slip Activity** | <br>Similar to the **Saga Activities** , **Routing Slip Activities**  are tasks to be performed within a **Routing Slip** . These, however implement the interface **IActivity** or **IExecuteActivity** . If the **Activity** needs to be **Compensated** (rolled back in case of a failure in another **Activity** within the same**Routing Slip** ), it should implement **IActivity** that will request for **Execute** and **Compensate** methods. The **Compensate** method should contain the process to undo all that had been done by that **Activity** when it was successfully executed.<br>Note that if a particular **Activity** in a **Routing Slip**  fails, its **Compensate** method will not be executed. When an exception is thrown by a **Routing Slip Activity** , **MassTransit** will use the **Routing Slip Activity Log**  to execute all the Compensate methods of all **Activities** that had executed successfully in that **Routing Slip** .<br>If an **Activity** does not need **Compensation** , it can simply implement **IExecuteActivity** that will only request the **Execute** method, but not the **Compensate** .<br> |
| **Itinerary** | <br>The list of ordered **Activities**  within a **Routing Slip** .<br> |
| **Choreography** | <br>The list of **Activities** within a **Routing Slip**  is dynamic. Each **Activity** owns the **Routing Slip Itinerary**  when it is executing and can change that **Itinerary** removing **Activities** or adding new **Activities** that were not part of that original **Itinerary** . This concept of an **Orchestration** that is dynamically determined on each step of the way is called **Choreography.**<br> |
